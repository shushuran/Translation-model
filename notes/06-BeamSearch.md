## 1. 算法

```
贪心：每步只保留 1 条最优前缀，走到底
Beam：每步保留 beam_size 条最优前缀，最后按长度归一化的对数概率选一条

每步：
  1. 对**每条** beam 算下一个词的对数概率分布
  2. 取概率最高的 beam_size 个词，展开出 beam_size² 个候选
  3. 生成 <eos> 的移入「已完成」池；其余按分数排序保留前 beam_size 条
  4. 跑到 max_len 或所有 beam 都收尾为止；最后从「已完成 ∪ 仍存活」里挑最优
```

### 为什么用对数概率之和

```
P(y) = Π p(y_t)            一长就下溢成 0（10 个 0.1 相乘 = 1e-10）
log P(y) = Σ log p(y_t)    变求和，数值稳定，且单调等价
```

### 长度惩罚（GNMT 式）

```
score = log P(y) / ((5 + |y|) / 6)^α
```

纯对数概率之和**天然偏好短句** —— 每多生成一个词就多一个负项（`log p ≤ 0`）。

实测 α 的影响（150 步的 checkpoint，beam=5）：

| α | 整句准确率 | token 准确率 | 平均输出长度 |
|---|---|---|---|
| 0.0 | 0.0000 | 0.3455 | 9.578 |
| 0.3 | 0.0000 | 0.3465 | 9.582 |
| 0.6 | 0.0000 | 0.3475 | 9.590 |
| 1.0 | 0.0000 | 0.3475 | 9.590 |
| 1.5 | 0.0000 | 0.3475 | 9.590 |

方向要注意（我第一遍又写反了）：**长度惩罚不降低短句的分数，而是抬升长句的分数**。
`|y| = 1` 时因子恰好是 1，所以短句分数不变。代入数字：

```
score(-10, 1)  = -10 / 1            = -10.000
score(-10, 2)  = -10 / (7/6)^0.6    =  -9.359
score(-10, 10) = -10 / (15/6)^0.6   =  -5.790
```

## 2. 正确性怎么保证：四项相互独立的检查

| # | 检查 | 为什么它能抓到问题 |
|---|---|---|
| ① | `beam_size = 1` 必须**逐位等于**贪心 | 两者是同一个算法在 K=1 时的退化，任何差异都是 bug |
| ② | 极小问题上 `beam_size ≥ 词表大小` 必须等于**暴力枚举** | 不剪枝时搜索空间就是全部序列，有了绝对参照物 |
| ③ | 返回的分数必须与**用教师强制前向独立重算**的 `Σ log p` 一致 | 验证内部累加没有错，而不是只验证它自洽 |
| ④ | `<eos>` 之后全是 `<pad>`，之前没有 `<pad>` | 验证终止逻辑 |

② 的实测（词表 4、长度 3，搜索空间 Σ4^k = 85 个节点）：

```
暴力枚举  [[2, 0, 0], [2, 0, 0]]  分数 [-1.386359, -1.386365]
beam(4)   [[2, 0, 0], [2, 0, 0]]  分数 [-1.386359, -1.386365]      ✓
```

`brute_force_decode` 会先估算节点数，超过上限就报错 —— 防止误用在大问题上
（V=27、max_len=10 时是 10¹⁴ 量级）。

## 3. Beam 存在的意义：一个能看见的例子

用一个随机初始化的极小模型（词表 4、长度 3）：

```
解码方式        样本 0 输出      样本 0 分数
贪心            [1, 2]          -2.7720
Beam 2          [2, 0]          -1.3860
Beam 4          [2, 0]          -1.3860
暴力枚举        [2, 0]          -1.3860
```

**贪心在第 1 步选了局部最优，却走进了更差的整体序列。**
Beam 因为保留了次优前缀，最终找到了真正的最优解。

`beam_size` 单调性（这个例子里 `beam=4` 就等价于穷举）：

```
beam_size=1   分数 [-2.7720, -1.3861]
beam_size=2   分数 [-1.3860, -1.3861]
beam_size=3   分数 [-1.3860, -1.3861]
beam_size=4   分数 [-1.3860, -1.3861]
```

## 4. ⚠ 本步踩到的大坑：提前停止把最优解丢掉了

### 现象

在 3000 步的 checkpoint（贪心整句准确率 **100%**）上：

```
beam_size=3   →  整句准确率 60.25%
beam_size=5   →  整句准确率 18.00%
```

**Beam 越大越差** —— 这本身就是"实现有问题"的强烈信号，
因为正确实现的分数不可能随候选变多而显著变坏。

### 定位

打印某条测试样本沿贪心路径的每步 top-4：

```
step7  in=9   top4=[('6', -0.0), ('5', -9.872), ('0', -10.367), ('9', -10.516)]
step8  in=6   top4=[('0', -0.0), ('6', -9.595), ('<eos>', -10.556), ('4', -11.309)]
step9  in=0   top4=[('<eos>', -0.0), ('6', -9.857), ('5', -10.887), ('0', -12.086)]
```

正确 token `'0'` 的对数概率是 **-0.0**，而 `'<eos>'` 是 **-10.556**。
正确序列的分数应该接近 0，但 Beam 返回的是分数 **-6.35** 的提前收尾序列
（`22/June/596<eos>`，少一个 `0`）。

### 原因

```python
if len(done) >= beam_size:
    break          # ← 错的
```

`done` 里攒够了 `beam_size` 条**不代表**存活 beam 里没有更好的候选。

在这个例子里：正确前缀当时还在 `beams` 里，下一步就能以 `log p ≈ 0` 收尾
（总分 ≈ 0）；但 `done` 里已经攒了 3 条 `log p ≈ -10` 的"提前输出 `<eos>`"
假设，于是循环被掐断，把一个分数 -6.35 的差答案当成了最优解。

### 修法

**不提前停**：跑到 `max_len` 或所有 beam 都收尾为止，
最后从「已完成 ∪ 仍存活」里一起挑。

```python
pool = done + [(tokens, logp) for tokens, logp, _ in beams]
best = max(pool, key=score)
```

代价最多是 `max_len × beam_size` 次单步解码，本项目完全可以接受。

修复后：

```
beam1/3/5/10 × α=0/0.6/1.5   →  整句准确率全部 1.0000（与贪心一致）
```

### 为什么"凑够就停"看起来天经地义

常见的实现里打分口径、长度惩罚、beam 的替换策略各不相同，很多细节会掩盖这个问题。
严谨的停止条件需要「已完成的最优分数 > 存活 beam 分数的**上界**」，
而**长度惩罚让这个上界很难算** —— 序列变长时分数不一定变差
（分母变大、分子也变负，比值可能上升）。所以这里选择最保守也最简单的做法。

### 固化成回归测试

用**脚本化的假模型**（按预设表返回 logits）精确复现：

```
从 <bos>:  A(1.0) B(0.7) C(0.4)
从 A/B/C:  <eos>(0.0)  D(~3.0)
从 D:      <eos>(5.0)
```

第 2 步时 `done` 就会攒到 3 条「提前收尾」假设（分数 -3.87），
但真正最优的是 `A→D→<eos>`（分数 -0.877），要到第 3 步才收尾。

```
[PASS] 构造的脚本里「晚收尾」确实更优   -0.8770 vs -3.8770
[PASS] 返回的是「晚收尾」的最优序列     [3, 6, 2]
[PASS] 分数等于该序列的对数概率         -0.877019 vs -0.877019
```

## 5. Beam 什么时候有用、什么时候没用

在不同训练程度的 checkpoint 上对比（测试集 400 条）：

| checkpoint | 贪心 token | Beam3 token | 结论 |
|---|---|---|---|
| 80 步 | 0.3256 | 0.2838 | **Beam 更差**（-0.042） |
| 150 步 | 0.4585 | 0.5101 | **Beam 更好**（+0.052） |
| 250 步 | 0.9528 | 0.9528 | 完全相同 |
| 400 步 | 0.9997 | 0.9997 | 完全相同 |
| 3000 步 | 1.0000 | 1.0000 | 完全相同 |

**三种结果都出现了**，这比"Beam 总是更好"有价值得多：

1. **模型很准、贪心已经最优**（250 步之后）→ Beam 与贪心逐位相同。
   搜索空间里没有更好的解，Beam 只是白白多花算力。
2. **模型不够准、确实存在局部最优陷阱**（150 步）→ Beam 有收益。
3. **模型分数本身就不靠谱**（80 步）→ **Beam 反而更差**。
   因为 Beam 优化的是**模型自己给的分数**，而"模型分数高"不等于"答案对"。
   此时贪心反而被"每一步都选最可信的词"这个保守策略救了。

> **核心结论**：Beam Search 不是免费的午餐，它优化的是**模型分数**而不是准确率。
> 它只在两个条件同时满足时有用：
> ① 模型的每步概率足够可信；② 搜索空间里确实存在贪心错过的更优解。
> 这也是为什么现代 NMT 系统在模型足够强之后，往往把 beam_size 从 10 降到 4~5 甚至用贪心。

## 6. 算力代价

一个 batch（`B=32, S=11, max_len=12`）：

| 方法 | 耗时(ms) | 相对贪心 | 单步解码次数 |
|---|---|---|---|
| 贪心 | 26.2 | 1.00 | 384 |
| Beam 3 | 209.1 | 7.97 | 1152 |
| Beam 5 | 340.9 | 12.99 | 1920 |
| Beam 10 | 692.7 | 26.40 | 3840 |

理论倍率是 `beam_size`（7.97 / 12.99 / 26.40 ≈ 8 / 13 / 26），实际常数因子更大
是因为本项目每步都要**重算一次注意力**（没有缓存 `W_k · H_seq`）。

另外，逐样本实现还有额外开销：为了代码清晰，我们循环了 `B` 次。
批量实现可以把 `(B × beam_size)` 当成一个 batch 并行算。

## 7. 本步踩坑记录

| # | 坑 | 怎么发现的 | 教训 |
|---|---|---|---|
| 1 | `if len(done) >= beam_size: break` 提前停止丢解 | Beam 越大效果越差（100% → 60% → 18%），逐样本打印每步 top-4 后定位 | **"结果随 beam 变大而显著变差"是实现有 bug 的信号，不是算法的性质** |
| 2 | 又以为长度惩罚"降低短句分数" | 测试失败，代入数字后确认是"抬升长句分数" | 归一化项的方向必须代入数字验算（第 5 步的偏差修正也是同一个坑） |
| 3 | α 扫描显示完全无影响 | 发现所有输出长度相同 → 惩罚因子是常数 → 不影响排序 | **"扫参数没有变化"要先怀疑是输出没有变化，而不是参数没生效** |
