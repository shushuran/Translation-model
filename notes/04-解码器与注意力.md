## 1. 完整数据流

```
src_ids (B,S) ──Embedding──▶ (B,S,D) ──GRU──▶ H_seq (B,S,H) ─┬─▶ attention 的 keys / values
                                                              └─▶ h_final ──▶ s₀ = tanh(W·h_final + b)

第 t 步（t = 0 … T-1，tgt_in[t] 就是 y_{t-1}）：
    c_t, w_t = attention(query = s_{t-1}, keys = H_seq, values = H_seq, mask = src_mask)
    x_t      = [ emb(y_{t-1}) ; c_t ]               ← context 拼进 GRU 输入
    s_t      = GRU(x_t, s_{t-1})
    logits_t = W_o · [ s_t ; c_t ]
```

一句话：**编码器把源句压成一组向量；解码器每生成一个词，就先用当前隐状态去这组向量里「查」一次（注意力），
把查到的 context 和上一个词的嵌入拼起来喂给 GRU，再投影成词表分布。**

实测形状（`B=4, S=11, T=10`）：

```
H_seq    (4, 11, 128)      h_final  (4, 128)      s₀ (4, 128)
logits   (4, 10, 27)       weights  (4, 10, 11)
注意力权重每步行和 = 1.000000    padding 位置权重最大值 = 0.000e+00
```

## 2. Bahdanau 式 vs Luong 式：本步最重要的架构分叉

| | Bahdanau (2015) | Luong (2015) |
|---|---|---|
| 算 context 的时机 | **先**用 `s_{t-1}` 算 `c_t` | **先**算 `s_t`，再用 `s_t` 算 `c_t` |
| context 用在哪 | 拼进 **GRU 的输入** | 只用在**输出层** |
| 注意力影响什么 | 状态更新 + 输出 | 只影响输出 |
| 天然配对 | 加性注意力 | 点积注意力 |

```
Bahdanau:  s_t = GRU([emb(y_{t-1}) ; c_t], s_{t-1})
Luong:     s_t = GRU(emb(y_{t-1}), s_{t-1}) ;  c_t = attn(s_t, H_seq)
```

代码差别只有「attn 在 cell 之前还是之后」，但语义不同：
**Bahdanau 式里 context 会改变循环本身**，Luong 式里循环是"纯"的、注意力只做输出端的检索。

本项目选了 Bahdanau 式（与加性注意力配对）。

## 3. 输出层吃什么：三种模式

| `output_mode` | 输出层输入 | 维度（H=128） | 说明 |
|---|---|---|---|
| `s_c` | `[s_t ; c_t]` | 256 | 默认，最简洁 |
| `s_c_emb` | `[s_t ; c_t ; emb(y_{t-1})]` | 320 | Bahdanau 原论文写法 |
| `s` | `[s_t]` | 128 | 消融基线：context 只能经隐状态间接影响输出 |

配置项化之后，第 8 步做消融只要 `dataclasses.replace(CONFIG.model, output_mode="s")`。

## 4. 初始隐状态：三种模式

| `init_mode` | s₀ | 参数量 |
|---|---|---|
| `bridge` | `tanh(W·h_final + b)` | 16,512（可学投影） |
| `direct` | `h_final` | 0（要求两边隐维度相同） |
| `zero` | `0` | 0（全靠注意力提供源句信息） |

`bridge` 是标准做法：多一个可学参数，让模型自己决定「怎么把编码器末状态变成解码器起点」。

## 5. 反向传播：三条必须**相加**的汇合路径

这是本步最容易写错的地方。每一步里都有两个张量被**用在两处**：

```
① context 用在两处  ->  dctx 要相加
      GRU 输入 [emb ; ctx]        -> dcell.x[E:]
      输出层   [s_t ; ctx]        -> do_t[H:]

② s_t 用在两处      ->  ds_t 要相加
      第 t 步的输出层             -> do_t[:H]
      第 t+1 步的 GRU 隐输入       -> ds_carry（从上一步反向传回来）

③ keys 和 values 是同一份张量 H_seq  ->  dsrc_h 要相加
      attention.backward 返回 dkeys 和 dvalues 两个梯度
      因为它们来自同一个 H_seq，必须叠加后一起传回编码器
```

写成代码：

```python
do_t  = self.out.backward(dlogits[:, t, :])
ds_t, dctx, _ = self._split_output_grad(do_t)
ds_t = ds_t + ds_carry                    # ②

dcell = self.cell.backward(ds_t)
dctx = dctx + dcell["x"][:, E:]           # ①
ds_prev = dcell["h"]

dattn = self.attn.backward(dctx[:, None, :])
ds_prev = ds_prev + dattn["query"][:, 0, :]   # query 就是 s_{t-1}
dsrc_h += dattn["keys"] + dattn["values"]     # ③ ← 漏了这里后果最严重
```

**负面对照实测**（故意只回传 `dkeys`，丢掉 `dvalues`）：

| 参数组 | 正确实现 | 漏掉一半 |
|---|---|---|
| 编码器 | 分歧/抖动 `1.7e+00` | **5 个张量 FAIL** |
| 解码器 | `1.7e+00` | `1.7e+00`（**全部通过**！） |

**这是本次最危险的一个 bug 形态**：只检验解码器参数的实现会「完全通过」，
而 loss 依然会下降（解码器自己在学）。最终表现是「模型能训练，但 encoder 几乎没学到东西」。
所以脚本第 [7] 节专门加了一条检查：**编码器每个参数的梯度必须非零**。

## 6. 单槽位缓存：这个模块里有**三个**模块中招

第 3 步的教训（`Module._cache` 只有一个槽位）在这里升级了。解码循环里：

| 模块 | 循环内调用次数 | 需要 save_cache？ |
|---|---|---|
| `self.attn` | T 次 | ✅ |
| `self.cell` | T 次 | ✅ |
| `self.out` | T 次 | ✅ **最容易漏** |
| `self.emb` | 1 次（整段 tgt_in 一次查完） | 不需要 |
| `self.bridge` | 1 次 | 不需要 |

`self.out` 最容易漏，因为它看起来是个"无状态的投影层"。
但在 teacher forcing 下每一步的输入 `o_t` 都不同，反向时必须回到对应的那一次。

> **检查清单**：写循环网络时，逐个模块问一句
> 「它在循环里被调用了几次？大于 1 就必须 save_cache。」

顺带把 `backward` 的语义统一了：**累加、不清零**，调用方负责 `zero_grad()`。
（原来 `GRUEncoder.backward` 和 `AttentionDecoder.backward` 内部偷偷清零，
导致「backward 两次梯度翻倍」的测试失败 —— 也算是个真实的不一致。）

## 7. 因果性：必须**验证**，不能假设

解码器是循环结构，第 t 步只吃 `tgt_in[:, t]`，所以天然满足因果性。
但这句话得验证，否则将来某次重构可能悄悄引入信息泄露。

实测：篡改第 t 步之后的输入，检查前 t+1 步的 logits：

```
篡改起点     前若干步 logits 最大差
t≥1          0.000e+00
t≥2          0.000e+00
...
t≥7          0.000e+00
```

全部严格为 0。同时反向验证「篡改第 2 步输入**必须**改变第 2 步输出」——
否则说明模型压根没用上输入（这种"反向验证"很重要，
只测"不该变的不变"可能只是因为模型输出恒定）。

## 8. 本步最大的收获：梯度检验的**适用边界**

### 现象

解码器端到端梯度检验里，`attn.W_q` 的相对误差是 **3.51e-02**，看起来像 bug。

### 诊断（不猜，直接测）

在梯度**最大**的那个元素上手工做中心差分：

```
attn.W_q idx=11362  解析 = 5.892959e-09
        ε=1e-6   数值 = 5.814793e-09
        ε=1e-5   数值 = 5.896672e-09
        ε=1e-4   数值 = 5.893064e-09
```

**数值估计随 ε 增大收敛到解析值**（相对差 `1.3e-3 → 9.8e-5 → 5.1e-6 → 3.1e-6`）。
这种行为只可能来自正确的解析梯度 —— 如果是噪声，估计值会乱跳；
如果公式错了，它会稳定收敛到**错误的值**。

### 原因

`attn.W_q` 的梯度只有 `5.9e-9`，而 loss 量级是 `0.136` —— **相差 8 个数量级**。

中心差分的舍入噪声下界是

```
noise_floor ≈ |L| · ε_mach / (2ε)  =  0.136 × 2.2e-16 / (2×1e-5)  ≈  1.5e-12
```

梯度只比噪声地板大 40 倍，相对误差自然被放大到 3%。

**为什么 W_q 的梯度这么小？** 初始化时编码器各位置的隐状态高度相似
（实测两两余弦相似度均值 0.43，最大 1.0 —— 冻结的 padding 位置完全相同），
导致 softmax 的雅可比 `w_s(dw_s - Σ_j dw_j w_j)` 中括号里的减项几乎抵消，
dscores 趋近于 0。这是"注意力在初始化时还分不清各个位置"的直接体现。

### 正确的判据：自校准

单一阈值（相对误差 < 1e-7）在这种情形下**根本不适用**。改成拿数值方法**自身的**不确定度当尺子：

```
spread      = |num(ε) - num(4ε)|        数值方法自身的抖动
discrepancy = |num(ε) - 解析梯度|        解析与数值的分歧
通过条件     discrepancy ≤ 10·( spread + 1e-6·|解析梯度| )
```

允许的误差取「数值方法自己的抖动」和「梯度的一个小比例」中较大者。

| 情形 | 谁主导 | 效果 |
|---|---|---|
| 梯度健康（远大于噪声） | `1e-6·|grad|` | 要求**相对精度** |
| 梯度贴着噪声地板 | `spread` | 只要求「与噪声水平一致」 |
| **公式写错** | 都不够 | `discrepancy` 与梯度同量级，远超两项 → **照样抓住** |

返回的 `ratio = discrepancy / max(spread, noise_floor)` 是最直观的一个数：
`O(1)~O(100)` 表示差异完全由噪声解释，`≫1e3` 表示公式错了。

实测：正确实现 `ratio ~ 1e0`，故意写错的实现 `ratio ~ 1e11`。

### 判据本身的测试

| 测试 | 结果 |
|---|---|
| 正确实现在 ε = 1e-6 / 1e-5 / 1e-4 下都通过 | ✓ |
| 解析梯度偏大 **0.1%** | 判 FAIL ✓ |
| 解析梯度偏小 **0.1%** | 判 FAIL ✓ |
| 解析梯度全零 | 判 FAIL ✓ |
| 真·低信噪比（`attn.W_q`） | 判 `low-snr`，**不误报 FAIL** ✓ |

**教训**：一个"只在数值正确时才通过"的检查才有价值；
但同样重要的是**它不能在数值不可判时误报失败**。
否则你会花一整天去"修"一个根本没错的公式。

## 9. 参数量与耗时

| 部分 | 参数量 |
|---|---|
| `emb` | 1,728 |
| `attn`（加性） | 33,024 |
| `cell` | 123,648 |
| `bridge` | 16,512 |
| `out` | 6,939 |
| **解码器合计** | **181,851** |

整模型：编码器 75,584 + 解码器 181,851 = **257,435** 参数。

一个 batch（`B=32, S=11, T=10`）前向 + 反向：**约 66~69 ms**
→ 一个 epoch（125 个 batch）约 **8.5 秒** → 3000 步约 **3.5 分钟**。

纯 NumPy 下这个速度可以接受 —— 数据只有 4000 条、序列只 10 步，
所以第 5 步真的能训到收敛，而不是只能跑个 demo。

## 10. 本步踩坑记录

| # | 坑 | 怎么发现的 | 教训 |
|---|---|---|---|
| 1 | `self.out` 在循环里被调用 T 次，缓存被覆盖 | 写 backward 时对照第 3 步的清单逐模块检查 | **循环网络里每个被多次调用的模块都要 save_cache** |
| 2 | `attn.W_q` 相对误差 3.5e-2 疑似 bug | 手工在最大元素上做 ε 扫描，发现收敛到解析值 | 单一阈值判据有适用边界；先诊断再改代码 |
| 3 | `GRUEncoder/AttentionDecoder.backward` 内部偷偷清零 | "backward 两次翻倍"测试失败 | backward 应累加，清零是调用方的责任（PyTorch 约定） |
| 4 | 测试里用「缩小输入」构造低信噪比 | 该测试失败：输入缩小会**同时**缩小 loss 和梯度，噪声地板跟着降 | 构造反例前先想清楚量纲 |
